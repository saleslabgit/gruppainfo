# Архитектура

## Текущее состояние

Приложение использует стандартную структуру Laravel 12 с небольшим доменным слоем для правил жизненного цикла:

- `app/Http` — HTTP-контроллеры и связанный с HTTP код;
- `app/Domain` — enum статусов, матрицы переходов, сервисы переходов и типизированный доступ к настройкам;
- `app/Models` — Eloquent-модели таблиц `gp_*` с явными именами таблиц и связями;
- `app/Providers` — провайдеры Laravel;
- `app/Support` — небольшие общие технические классы форматирования;
- `routes/web.php` — публичные, гостевые и защищённые role-specific web-маршруты, а также защищённая окружением UI-kit поверхность;
- `resources/views/components/ui` — общие Blade-примитивы дизайн-системы;
- `resources/views` — Blade-layout и страницы;
- `public` — document root и все готовые CSS/JS-файлы;
- `config` — конфигурация Laravel;
- `tests` — unit- и feature-тесты.

Stage 5 добавил административное управление психологами и их приватными документами. Stage 6 добавил кабинет психолога. Stage 7 реализует внутренний CRUD групп, moderation workflow и ручную активацию без банка. Публичная анкета, email-onboarding, lifecycle после активации, заявки и платежи в эти модули не входят.

## Аутентификация и доступ

Единый login использует стандартный Laravel `web` guard с Eloquent provider и session driver. `LoginRequest` выполняет server-side validation, допускает вход только для активного `approved`/enabled пользователя и ограничивает попытки по нормализованной паре email/IP. После успешного входа session ID регенерируется, а пользователь направляется в `/admin` или `/cabinet` по признаку `admin`.

Все защищённые маршруты последовательно проходят `stale-session`, `auth`, `eligible` и role middleware. Pre-auth слой читает идентификатор через API session guard и завершает сессию, если соответствующая запись уже soft-deleted или отсутствует, поэтому восстановление записи не оживляет старую browser-сессию. Обычный Eloquent auth provider по-прежнему не видит soft-deleted пользователей. `eligible` заново читает существующего пользователя и немедленно завершает текущую сессию, если статус больше не `approved` или установлен `disabled`. Role middleware оставляет две явные взаимоисключающие границы: administrator и psychologist; нарушение границы возвращает 403.

`App\Domain\User\UserSessionInvalidator` удаляет все записи настроенной database session table для одного пользователя через настроенное session connection. Сервис не зависит от текущего HTTP request и является точкой повторного использования для disable/reject/delete в Stage 5.

Маршруты `/admin/psychologists` остаются внутри цепочки `stale-session -> auth -> eligible -> role:admin`. Дополнительно каждый controller action использует `UserPolicy` или `UserDocumentPolicy`: middleware не является единственной границей авторизации, а попытка подставить administrator ID вместо psychologist ID возвращает 403.

Маршруты `/cabinet`, `/cabinet/groups` и `/cabinet/profile` используют ту же цепочку с границей `role:psychologist`; `/cabinet` перенаправляет в основной раздел групп. Профиль не принимает идентификатор пользователя: `CabinetController` получает текущего психолога только из authenticated request, явно проверяет `UserPolicy::viewOwnProfile` и заранее загружает `educationType` и `documents`. Выдача документа не дублируется в кабинете и по-прежнему проходит через общий `UserDocumentController` и owner-or-admin `UserDocumentPolicy`.

Ресурсные group actions дополнительно защищены `GroupPolicy`. Психолог видит только группы с собственным `owner_id`, редактирует только `draft`/`revision` и удаляет только `draft`/`rejected` без успешного непогашенного платежа. Администратор работает со всеми группами, но отдельное cleanup-действие допускает только `draft`/`awaiting_payment`. Для изменяющих действий policy повторно проверяется по строке, полученной с `lockForUpdate`, чтобы stale route model не обходила актуальный статус.

## Доменная модель

Статусы пользователя, группы и платежа представлены string-backed enum. Допустимость перехода задаётся методом `canTransitionTo`; изменение сохранённой модели выполняют только соответствующие сервисы в `app/Domain`. Переход группы и запись `gp_group_status_history` выполняются одной транзакцией. История фиксирует прежний и новый статус, пользователя-автора либо системного автора и необязательный комментарий.

`status` является единственным источником стадии жизненного цикла. Legacy-поле `accept` остаётся в таблицах для будущего контролируемого отображения старых данных, исключено из mass assignment и не используется доменной логикой. `disabled`, `free` и `admin` остаются независимыми признаками.

`GroupWorkflowService` координирует составные операции вокруг существующего `GroupStatusTransitionService`. Переходы Stage 7 выполняются только по матрице `draft → moderation`, `revision → moderation`, `moderation → revision/rejected/approved`, `approved → active`; комментарии/причины и activation-поля записываются в общей транзакции с переходом. Активация читает `placement_duration_days` через `SettingService`, фиксирует снимок срока и рассчитывает UTC `published_at`/`expires_at`. Создание всегда даёт `draft`, сохраняет реальный tariff snapshot владельца и не создаёт `gp_payments`; `awaiting_payment` не достижим из Stage 7 web actions.

Основные сущности используют soft delete. Исторические, финансовые данные и заявки защищены ограничивающими внешними ключами; nullable-ссылки на автора истории и платёж из webhook обнуляются при физическом удалении связанной записи. Email уникален среди активных пользователей через stored generated column `active_email`; техническая колонка скрыта моделью и не используется бизнес-логикой.

Значимые административные действия над психологом записываются в append-only таблицу `gp_user_action_history`. Запись сохраняет target, administrator actor, стабильный action code, status transition и только небольшой JSON-контекст изменения признака. `PsychologistAdminService` объединяет status transition и audit в одной транзакции и повторно использует `UserSessionInvalidator` для reject, disable и soft delete. Анкетное редактирование не может менять status, tariff, access, role, password или legacy `accept`.

`gp_user_documents` содержит только метаданные и случайный внутренний путь. Байты хранятся на private local disk (`storage/app/private`), не имеют public URL и выдаются только `UserDocumentController` после policy-проверки owner-or-admin. Upload проверяет байты через `fileinfo`, допускает только PDF/JPEG/PNG и удаляет сохранённый файл при ошибке записи метаданных. Admin delete удаляет файл и строку документа; soft delete психолога документы не удаляет.

Справочники разделены на определения и элементы. Seed создаёт только определения `education_type`, `group_format` и `gender`; значения элементов должны быть утверждены отдельно. Настройки хранят тип вместе со значением, читаются через `SettingService`, кэшируются по стабильному ключу и явно инвалидируются при записи.

## Границы для следующих этапов

- HTTP-контроллеры, request-валидация и middleware остаются в `app/Http`;
- Blade-страницы и будущие компоненты остаются в `resources/views`;
- интеграции с банком, почтой и внешним каталогом отделяются от доменной логики в инфраструктурных классах;
- контроллеры и шаблоны не меняют статусы и не запрашивают `gp_settings` напрямую.

Контроллеры и Blade-шаблоны не должны самостоятельно выполнять переходы статусов, денежную арифметику, преобразование часовых поясов или прямую работу с внешними системами.

## Дата и время

Приложение и база данных работают в UTC (`APP_TIMEZONE=UTC`). Для пользовательского отображения применяется `Europe/Minsk` через единый `App\Support\DateTimeFormatter`. В отдельных Blade-страницах не следует вручную менять часовой пояс. Логика сроков должна оставаться в UTC.

## Деньги

Денежные значения хранятся целыми числами в минорных единицах. `App\Support\MoneyFormatter` принимает только `int`, форматирует две минорные цифры и по умолчанию использует `BYN`. `App\Support\MoneyParser` преобразует пользовательский BYN-ввод строковыми операциями с проверкой точности. Арифметика через `float` запрещена.

## Frontend

Blade загружает скомпилированный Bootstrap 5.3.8 из `public/vendor/bootstrap`, затем проектный слой токенов и компонентов `public/app.css`. JavaScript загружается из локального Bootstrap bundle, Lucide и `public/app.js`. Bootstrap отвечает за низкоуровневое поведение dropdown/modal/offcanvas, а проектный CSS — за утверждённый внешний вид. CDN, Node.js, npm, Vite и frontend build step отсутствуют.

`DESIGN_SYSTEM.md` является источником явных визуальных значений и правил реализации, а `uikit/index.html` — утверждённым визуальным референсом для замысла, не разрешённого этим документом. Файлы `uikit/` служат только референсом и не являются runtime-зависимостью Laravel-приложения. Реализованный baseline находится в `resources/views/components/ui`; verification-страница собирается из тех же компонентов и production CSS/JS. Будущие страницы должны использовать этот namespace без локального копирования или переопределения стилей.

Специализированные компоненты полного каталога реализуются инкрементально перед первым продуктовым использованием. Stage 5 добавил общие Chip, Filters с mobile Drawer, Key-Value / Description List, File Upload и File / Document Item. Stage 7 добавил общие Money Input и Timeline; все они демонстрируются на `/ui-kit`. Если общего компонента ещё нет, продуктовая страница не создаёт ему визуальную замену. Отсутствующие или unresolved дизайн-решения требуют отдельного утверждения.

Montserrat 9.000 поставляется локальным variable-файлом Google Fonts с диапазоном weight 400–700 и OFL. Lucide закреплён на browser-ready UMD distribution 1.31.0 с ISC. Оба каталога находятся в `public/vendor`; контрольные суммы записаны в `docs/development.md`, приложение не загружает `uikit/` и не обращается к CDN.

Дизайн-система определяет визуальные правила, но не отменяет ограничения проекта по архитектуре, безопасности, стеку и локальной доставке ассетов.

Docker используется только для разработки. Приложение остаётся обычным Laravel-проектом, пригодным для размещения вне Docker с document root, направленным на `public/`.
